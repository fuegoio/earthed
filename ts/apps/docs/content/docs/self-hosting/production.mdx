## Reverse proxy

Neither service terminates TLS directly. Put both behind a reverse proxy (nginx, Caddy, Traefik).

Example nginx configuration. The API runs on its own subdomain (`api.your-domain.com`); the web app is served from the main domain.

```nginx
server {
    listen 443 ssl;
    server_name api.your-domain.com;

    ssl_certificate /path/to/cert.pem;
    ssl_certificate_key /path/to/key.pem;

    location / {
        proxy_pass http://localhost:8080;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}

server {
    listen 443 ssl;
    server_name your-domain.com;

    ssl_certificate /path/to/cert.pem;
    ssl_certificate_key /path/to/key.pem;

    location / {
        proxy_pass http://localhost:3000;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

## Marketing site as the front door

To host the marketing site and the app on the same domain (e.g. `earthed.app`), run the `website` container in front of the `web` container. The website is an Astro SSR server that serves its own pages and proxies every other path to the app — add a page under `src/pages/` and it's served instead of proxied. Logged-in visitors of `/` get the app (the website reads the `limen_session` cookie and proxies `/` to the app); logged-out visitors get the marketing page. Unknown paths fall through to the app, which handles its own auth (e.g. unauth `/feeds` redirects to `/login`).

Point the website at the app with `APP_URL`:

```
# website container
APP_URL=http://web:3000
```

Self-hosted deployments that don't want the marketing site skip the `website` container and expose the `web` container directly — `/` then redirects logged-out visitors to `/login` as usual.

## Cross-origin sessions

When the API and the web app are served from different origins (e.g. `api.earthed.app` and `app.earthed.app`), the default session cookie is host-only on the API domain, so the web app never receives it. How you fix this depends on whether the two share a registrable domain.

### Same registrable domain (subdomains)

If the API and web app share a registrable domain (e.g. `api.earthed.app` and `app.earthed.app` both under `earthed.app`), set the cookie `Domain` to that registrable domain. The browser then sends the session cookie to both the web app and the API (requests between them are same-site, so the default `SameSite=Lax` works):

```
EARTHED_COOKIE_SECURE=true
EARTHED_COOKIE_DOMAIN=earthed.app
EARTHED_TRUSTED_ORIGINS=https://app.earthed.app
```

`EARTHED_COOKIE_DOMAIN` must be a bare host (no scheme or path). `Secure` requires the API to be served over HTTPS.

### Different registrable domains

If the API and web app are on entirely different registrable domains (e.g. `api.earthed.app` and `myapp.com`), a shared cookie domain is not possible. Use `SameSite=None` so the browser sends the cookie cross-site:

```
EARTHED_COOKIE_SECURE=true
EARTHED_COOKIE_SAMESITE=none
EARTHED_TRUSTED_ORIGINS=https://myapp.com
```

`SameSite=None` without `Secure` is rejected by browsers, so the API rejects that combination at startup. Set `EARTHED_TRUSTED_ORIGINS` to the web app origin(s) so the API only returns `Access-Control-Allow-Credentials` for trusted frontends. The value of `EARTHED_WEB_URL` is always added to the allowlist automatically, so you only need to list any additional origins.

## Database backup

All feeds, entries, folders, and feed lists are in PostgreSQL. Back it up regularly.

```bash
# Create a backup
docker compose exec postgres pg_dump -U earthed earthed > backup.sql

# Restore from a backup
cat backup.sql | docker compose exec -T postgres psql -U earthed earthed
```

Schedule `pg_dump` with a cron job and store backups off-site for automated backups.
