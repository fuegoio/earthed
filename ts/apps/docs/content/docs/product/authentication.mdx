---
title: Authentication
description: Authenticate with the Earthed API using session cookies or bearer tokens.
---

All endpoints under `/v1/` require authentication. The only exception is `GET /v1/health`.

Earthed supports two credential types:

- **Session cookie** — used by the web frontend. The browser sends it automatically after sign-in.
- **Bearer token** — used by the CLI, scripts, and custom integrations. Send it in the `Authorization` header.

When both are present, the bearer token takes precedence.

All data is scoped per user — you can only read and write your own feeds, entries, folders, and tokens.

## Device flow (CLI login)

The CLI logs in via [RFC 8628 device authorization grant](https://datatracker.ietf.org/doc/html/rfc8628).
The CLI requests a device code from the API, opens a browser to a
confirmation page on the web frontend, and polls the API until the user
approves or denies the request.

```
POST /auth/device/code     → issue a device code (public)
POST /auth/device/token    → poll for the result (public)
POST /auth/device/confirm  → approve or deny (requires session)
GET  /auth/device/status   → check status by user code (requires session)
```

Tokens issued via the device flow expire after 14 days and are labeled
`CLI (device flow)` in the token list so they can be identified and
revoked. The plaintext token is never exposed to the web UI — it is
returned only to the CLI that initiated the flow.

## Session authentication

Session endpoints live at `/auth/` and do not require authentication.

Sign up:

```bash
curl -X POST http://localhost:8080/auth/signup \
  -H "Content-Type: application/json" \
  -d '{"email":"user@example.com","password":"your-password"}'
```

Sign in to get a session cookie:

```bash
curl -X POST http://localhost:8080/auth/signin \
  -H "Content-Type: application/json" \
  -d '{"email":"user@example.com","password":"your-password"}' \
  -c cookies.txt
```

Pass the cookie in subsequent requests:

```bash
curl http://localhost:8080/v1/me \
  -b cookies.txt
```

> **Email and password reset:** Verification and reset tokens are printed to the server's terminal output instead of being emailed. Check your terminal and open the URL from the logs. Wire a real mailer before deploying to production.

## API tokens

API tokens are prefixed with `pla_` and stored as SHA-256 hashes. The raw token value is shown only once at creation — save it immediately.

Create a token (requires an active session or an existing token):

```bash
curl -X POST http://localhost:8080/v1/tokens \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer pla_existing-token" \
  -d '{"label":"my-script"}'
```

```json
{
  "id": 1,
  "label": "my-script",
  "token": "pla_a1b2c3d4e5f6789012345678901234567890abcdef1234567890abcdef12345678",
  "created_at": "2025-08-14T12:00:00Z"
}
```

Use the token:

```bash
curl http://localhost:8080/v1/feeds \
  -H "Authorization: Bearer pla_a1b2c3d4e5f6..."
```

List tokens (raw values are never returned, only labels and metadata):

```bash
curl http://localhost:8080/v1/tokens \
  -H "Authorization: Bearer pla_your-token"
```

Revoke a token by ID:

```bash
curl -X DELETE http://localhost:8080/v1/tokens/1 \
  -H "Authorization: Bearer pla_your-token"
```

Requests using a deleted token fail immediately with 401.

## Token format

Tokens follow the format `pla_` followed by 64 hex characters (32 random
bytes). They are 69 characters long.

Tokens created via the web UI or the `tokens create` command do not
expire. Tokens issued via the device flow (`earthed login`) expire
after 14 days.

## CORS

The API enables permissive CORS for all origins. When an `Origin`
header is present in the request, the API reflects it back with
`Access-Control-Allow-Credentials: true`. When no `Origin` header is
present, `Access-Control-Allow-Origin: *` is used.

Allowed methods: GET, POST, PUT, PATCH, DELETE, OPTIONS.
Allowed headers: Accept, Authorization, Content-Type, X-Requested-With.
