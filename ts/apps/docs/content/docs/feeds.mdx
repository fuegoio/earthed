title: Managing Feeds
description: Subscribe to feeds, organize them with categories, and understand how the refresh pipeline works.
---

Feeds are RSS, Atom, or JSON Feed subscriptions. Planetary fetches and
parses them in the background, stores entries, and keeps them up to date
with adaptive polling.

## Subscribe to a feed

Create a feed subscription by providing the feed URL:

```bash
curl -X POST http://localhost:8080/api/v1/feeds \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer pla_your-token" \
  -d '{"feed_url":"https://blog.golang.org/feeds/posts/default"}'
```

When you subscribe, the `site_url` and `title` are temporarily set to
the feed URL. After the first refresh, they are updated to the real
values from the feed content.

You can assign a feed to a category at creation time:

```bash
curl -X POST http://localhost:8080/api/v1/feeds \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer pla_your-token" \
  -d '{"feed_url":"https://blog.golang.org/feeds/posts/default","category_id":2}'
```

Duplicate subscriptions (same URL for the same user) return a 400 error.

## List feeds

List all subscriptions:

```bash
curl http://localhost:8080/api/v1/feeds \
  -H "Authorization: Bearer pla_your-token"
```

Feeds are ordered by title. The response includes scheduling metadata:
`next_check_at` (when the scheduler will next try to refresh the feed)
and `last_fetch_at` (when the feed was last successfully fetched).

## Get a single feed

```bash
curl http://localhost:8080/api/v1/feeds/1 \
  -H "Authorization: Bearer pla_your-token"
```

## Delete a feed

Unsubscribe from a feed. All entries belonging to the feed are deleted
permanently.

```bash
curl -X DELETE http://localhost:8080/api/v1/feeds/1 \
  -H "Authorization: Bearer pla_your-token"
```

## Mark all entries as read

Mark every unread entry in a feed as read in one operation:

```bash
curl -X POST http://localhost:8080/api/v1/feeds/1/mark-all-read \
  -H "Authorization: Bearer pla_your-token"
```

## Categories

Categories organize feeds into groups. Create a category:

```bash
curl -X POST http://localhost:8080/api/v1/categories \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer pla_your-token" \
  -d '{"title":"Technology"}'
```

List categories:

```bash
curl http://localhost:8080/api/v1/categories \
  -H "Authorization: Bearer pla_your-token"
```

Delete a category. Feeds in the deleted category are not deleted — they
become uncategorized:

```bash
curl -X DELETE http://localhost:8080/api/v1/categories/2 \
  -H "Authorization: Bearer pla_your-token"
```

## How feed refreshing works

Planetary runs a background scheduler that periodically checks for feeds
due for refresh. The pipeline has four stages:

1. **Fetch** — the feed URL is fetched with conditional headers
   (`If-None-Match` / `If-Modified-Since`). If the server returns 304 Not
   Modified, the feed is skipped and the next check is scheduled in 60
   minutes.

2. **Parse** — the response body is parsed based on content type and
   format. Planetary supports RSS 2.0, Atom 1.0, and JSON Feed.

3. **Sanitize** — entry HTML content is sanitized through an allowlist.
   Unsafe tags and attributes are stripped. Links get
   `rel="noopener noreferrer"`. `javascript:` and `data:` URLs are
   blocked. See [Architecture](/docs/architecture) for the full list of
   allowed HTML.

4. **Store** — entries are deduplicated by a SHA-256 hash of the link,
   title, and publication date. New entries are inserted; existing ones
   are skipped. Media attachments (enclosures) are stored separately.

### Adaptive polling

The scheduler does not poll every feed at a fixed interval. Instead, it
estimates the ideal refresh frequency based on the feed's average
publication cadence:

- The average interval between the most recent items is calculated.
- The interval is clamped to a minimum of 10 minutes and a maximum of 24
  hours.
- If there are fewer than two items with parseable dates, the default
  interval is 60 minutes.

This means frequently-updated feeds are checked more often, while
infrequent feeds save resources.

### Error handling

When a fetch or parse error occurs:

- The `parsing_error` field is set to the error message.
- The `parsing_error_count` is incremented.
- The next check is scheduled in 15 minutes.

When the feed is successfully fetched and parsed again, the error
fields are cleared and the count resets to 0.

### Scheduler configuration

The scheduler runs by default. Configure it with environment variables:

| Variable | Default | Description |
| -------- | ------- | ----------- |
| `PLANETARY_POLLING_FREQUENCY` | `60s` | How often the scheduler checks for due feeds |
| `PLANETARY_BATCH_SIZE` | `100` | Max feeds processed per scheduler tick |
| `PLANETARY_WORKER_POOL_SIZE` | `5` | Concurrent feed-processing workers |
| `PLANETARY_HTTP_CLIENT_TIMEOUT` | `20s` | Timeout for fetching a single feed |
| `PLANETARY_HTTP_CLIENT_MAX_BODY` | `15728640` | Max feed body size in bytes (15 MB) |
| `PLANETARY_DISABLE_SCHEDULER` | (unset) | Set to any non-empty value to disable |

See [Self-Hosting](/docs/self-hosting) for all environment variables.
